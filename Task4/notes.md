# Задание 4. Проектирование продажи ОСАГО

## 1. Сервис osago-aggregator
- **Хранилище:** Да, используется `osago-aggregator-db` (PostgreSQL)
для хранения состояния заявок и полученных предложений. Это необходимо,
так как сервис работает в нескольких экземплярах и должен иметь общее состояние (stateless-архитектура).
- **API для core-app:** 
  - REST (синхронный) для создания заявки на ОСАГО.
  - WebSocket/SSE (асинхронный) для стриминга предложений от страховых компаний по мере их поступления.

## 2. Взаимодействие с веб-приложением
- **API для веб-приложения:** 
  - REST для отправки заявки.
  - WebSocket/SSE для получения предложений в реальном времени (чтобы отображать их сразу, без ожидания самой
медленной страховой).
- **Интеграция:** Используется комбинация REST (запрос) + WebSocket/SSE (ответ).

## 3. Паттерны отказоустойчивости
На стрелке от `osago-aggregator` к страховым компаниям применены:
- **Circuit Breaker:** для защиты от недоступных страховых компаний (размыкание цепи при серии ошибок).
- **Retry:** повторные попытки при сетевых сбоях с экспоненциальной задержкой.
- **Timeout (60s):** жесткое ограничение времени ожидания ответа от страховой.
- **Rate Limiting:** ограничение количества запросов в соответствии с квотами страховых компаний.

## 4. Зависимость от количества экземпляров
- Сервис `osago-aggregator` работает в нескольких экземплярах. Хранение состояния в общей БД (`osago-aggregator-db`)
позволяет любому поду обработать запрос и сохранить результат.
- Для синхронизации WebSocket-соединений между подами (если потребуется) используется механизм Pub/Sub
(например, Redis или Kafka).
